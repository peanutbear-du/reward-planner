## Contract and request semantics

`POST /api/commands/wish/create`

```json
{ "title": "Camera", "target": 137, "referencePrice": 123.45, "why": "Learn photography" }
```

title is trimmed and required. target accepts presets and custom positive integers, bounded to PostgreSQL integer (2147483647). referencePrice is optional/null or a finite nonnegative JSON number (zero allowed, no coercion or price-to-target conversion). No invented two-decimal or currency rule. Why is optional/null, trimmed; blank becomes null. Omitted optional fields normalize to null. Unknown fields, including userId, status, progress, id and coverPath, reject. Price interpretation/precision beyond this validation is not an allocation rule; the DB column remains numeric.

Response: `{ data: { wish: CreatedWishDto }, effects: ["wish_created"] }`. The Wish includes id/title/target/referencePrice/why/createdAt/updatedAt, status=wishlist, and null coverPath/startedAt/unlockedAt/redeemedAt. Private or unknown persistence columns are not forwarded. Runtime parsing rejects malformed/mismatched returned values or a non-Wishlist result.

Each POST is a distinct creation, as with existing Create Task. Repeated titles are allowed; this ticket adds neither title uniqueness nor idempotency storage/keys. Tests verify separate dispatches and mock-generated identities, **not database idempotency or concurrency**. A transport failure can occur after commit; the Client never retries automatically, and a future caller must reconcile uncertain outcomes before submitting another create. Exactly-once creation is not claimed.

Failure mapping: malformed/invalid input 400 INVALID_REQUEST; missing/invalid identity 401 UNAUTHORIZED; RPC authentication/validation errors 401 AUTHENTICATION_REQUIRED / 400 INVALID_WISH_REQUEST; missing RPC/table contract 503 WISH_CREATION_UNAVAILABLE (PGRST202/PGRST205/42P01/42883). Unexpected auth/database/transport failures return generic 500, without database details. The endpoint is wired but remains unavailable until its dependencies are installed; it never pretends persistence succeeded.

### Contract / security / side effects

1. Signature and p_title/p_target/p_reference_price/p_why names match the existing Adapter; defaults for omitted metadata are NULL. Return is exactly `{wish: CreatedWishDto}` with twelve explicit camelCase fields; user_id/private columns are omitted. 2. auth.uid() is required, client user_id/status are not accepted. SECURITY DEFINER uses empty search_path; relations and function calls are explicitly qualified. EXECUTE is revoked from PUBLIC/anon/authenticated/service_role and regranted only to authenticated. 3. The only business write is one INSERT into wishes with status=wishlist and cover/start/unlock/redeem fields explicitly NULL. No reward, Pending, allocation, current-Wish switch or storage operation. Source/profile FKs and table constraints remain authoritative.
4. Trim semantics explicitly enumerate ECMAScript's 25 WhiteSpace/LineTerminator characters with a PostgreSQL Unicode string literal, used as btrim's character set for title and Why. Blank Why becomes NULL; inner whitespace survives. NBSP/BOM/Unicode spaces are handled consistently with the existing Zod .trim(); U+0085/U+180E/U+200B are not trim characters. The retained M3-01 title CHECK may independently reject locale-defined whitespace-only content; the RPC checks that same condition and returns INVALID_WISH_REQUEST rather than weakening it.
5. Positive integer target is enforced by the integer argument plus validation. Fractional integer text / overflow can fail during argument conversion before the function; HTTP Zod rejects those earlier. Price rejects negative, NaN, infinities and numeric values greater than the finite JavaScript-number upper bound (1.7976931348623157e308). The latter is a DTO representation bound, not a currency/price business limit. NULL and zero remain valid; no decimal rounding policy is introduced.
6. BEGIN/COMMIT wrap migration installation only. No function-internal COMMIT/ROLLBACK. One RPC call is one transaction; insert/constraint failures propagate without returning success. No idempotency table/key, upsert, title uniqueness or automatic retry. Each successful invocation creates a distinct identity.
