Response includes source date/Item/Plan, `resultStatus: cancelled`, `changed` and a `daily_item_cancelled` effect only for an actual change. Invalid requests/authentication, missing resources and illegal states map to 400/401/404/409; private unexpected database details are not returned.

## SQL / transaction / ownership review

- Migration contains five top-level statements: BEGIN, CREATE FUNCTION, REVOKE, GRANT, COMMIT. Dollar-quoted function body remains one statement. No LOCK TABLE, SET LOCAL, table-wide lock, backfill or replacement trigger is introduced.
- All **11 existing migrations** were compared against HEAD with line endings normalized: unchanged. New migration has **not been deployed**. Static splitting/source review is not PostgreSQL compilation or database execution.
- SECURITY DEFINER, empty search_path, auth.uid() required; source Plan/Item and every Task/Planning lookup/write explicitly filter by owner. The client cannot supply a separate Task ID or user ID.
- EXECUTE revoked from PUBLIC/anon/authenticated/service_role, then granted only to authenticated. No table privileges or RLS policies are broadened. The API uses the authenticated user-scoped client; no privileged credential enters Desktop.
- Lock order follows existing commands: source Plan → related Task, when present → source Item → Planning. The initial owned Item read resolves the target without locking it; the locked reread rechecks target identity. No later destination Plan lock is acquired.
- Already-cancelled returns changed=false without a Planning or Item write, including when a later arrangement uses the original source date again. Completed/rescheduled/incomplete and Draft/missing/foreign contexts reject before writes.
- Pending cancellation changes only Item result_status/updated_at. Planning is retained; only a live matching planned_date is cleared, with updated_at changed. Existing time/week/other fields remain. Other/null/missing Planning is untouched; no row is inserted.
- Task fields, snapshots, origin/priority, completed_at_on_day, rescheduled_to_date and target identity are preserved. Existing Milestone-targeted Item relations use their own owned Planning relation without introducing Milestone execution/UI/business logic.
- Planning cleanup, Item update and existing qualification/reward triggers execute in the same RPC transaction. Exceptions propagate; no caught failure allows partial success. Pending/cancelled both remain incomplete denominator members, so counters/qualification and existing Reward Events should remain identical.
- Same-source concurrent commands serialize on the Plan and recheck the stored Item state. Task locking also coordinates schedules/execution across dates. These are static concurrency findings, **not an executed race/deadlock proof**.
