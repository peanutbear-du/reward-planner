## Structure / security review

- Wishes contains exactly the specified business fields. UUID identity, profile FK with owner deletion cascade, nonblank title (including tab/newline-only rejection), positive integer target, four allowed statuses, nullable optional fields and initial created/updated timestamps. Reference price is separate numeric metadata, not the progression target.
- Partial unique index on user_id WHERE status='unlocking' enforces at most one current Wish, including concurrent writes. Wishlist has no per-owner uniqueness limit. started_at and allocations can survive a later switch back to Wishlist. No progress cache, timestamp/state-transition trigger or automatic unlock is installed.
- The existing Daily-only reward_events table is reused. The only alteration is adding UNIQUE `(id, user_id)` for an owner-aware Allocation FK. No old migration, reward row, source constraint, amount constraint, function, trigger, ACL or RLS policy is changed. `MILESTONE_COMPLETED` remains disallowed until an owned Milestone source relation is introduced later.
- Each Allocation requires an Event and owner. Composite Event and Wish FKs prevent cross-user references even under privileged writes. `wish` requires wish_id; `pending` requires NULL wish_id. Source type is obtained through its Event, without redundant or unvalidated source fields.
- The user explicitly confirmed **nonzero signed integer amounts**, reserving negative rows for later append-style corrections. Multiple rows for one source/target allow splits and future Pending transfers. No unique constraint would collapse corrections into a single record. No engine, sum/cap enforcement or balance policy is implemented here.
- Both new tables enable RLS, revoke all table privileges from PUBLIC/anon/authenticated, and grant authenticated SELECT only with auth.uid()=user_id. No direct client writes are opened. service-role bypasses RLS and must remain server-only; no credential is added to Desktop.
- Event/Wish references use non-deferrable NO ACTION on standalone deletion: referenced history cannot silently disappear or turn a Wish allocation into Pending. Profile deletion cascades all owned relations together. Future delete functionality, if ever added, must respect this dependency; it is not added in this ticket.
- Migration wraps all 15 top-level statements in explicit BEGIN/COMMIT. No explicit LOCK TABLE or SET LOCAL, Command/RPC, trigger replacement or data backfill. Adding the composite UNIQUE key still requires PostgreSQL's normal DDL lock/index work on reward_events; schedule/review deployment accordingly. There is no concurrent-index workaround or unnecessary explicit table lock.

## Future M3-05 / M3-06 / M3-07 responsibilities

The approved signed representation is a persistence capability, **not permission to create negative balances or duplicate compensation**. Future server Commands must define and atomically enforce source totals, Pending consumption, overflow, valid corrections/idempotency, lock order, and protection for Unlocked/Redeemed Wishes. The Event remains the original earned +N source; its amount is not rewritten by allocation splits.

The schema does not force a final progress formula. Neither a naive sum of every row nor blindly dropping all reversed Events is specified as correct: later Commands must preserve unlocked history while applying valid corrections to eligible progress. No additional correction-reference/status/idempotency fields are invented before those Commands need a concrete contract. Further incremental schema work may accompany that implementation if necessary.
