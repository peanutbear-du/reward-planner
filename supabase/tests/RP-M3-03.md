## API / validation

- `POST /api/commands/wish/cover-upload`: Bearer auth first, multipart fields exactly wishId and file, no duplicates/extra path fields. HTTP 201 returns `{data:{wishId,coverPath},effects:["wish_cover_uploaded"]}`. Filename is ignored, including extensions; MIME and bytes decide validity.
- Actual multipart bytes are capped at 5 MiB + 64 KiB envelope overhead before FormData decoding, even without Content-Length. File cap is exactly **5,242,880 bytes** (5 MiB), inclusive. MIME must be image/jpeg, file nonempty, with JPEG SOI/marker prefix and final EOI signature. This is signature sniffing, not full image decoding; it does not promise every corrupt/polyglot JPEG is rejected as a decoder would. No pixel inspection/transcoding, EXIF stripping or image processing is performed.
- Authenticated user-scoped Wish lookup uses existing SELECT RLS. Missing/foreign Wish → 404; existing cover → 409 before privileged client creation. Only after bytes and owned Wish pass is the server writer constructed. Upload uses upsert=false; object collision → 409 and no association/delete. Existing cover cannot be overwritten.
- `GET /api/wishes/cover?wishId=UUID`: same authenticated owned-Wish lookup, canonical key validation and user-scoped Storage signing, returning a **300-second signed URL** with private/no-store. Missing cover → 404. The URL is never stored in the database or audit logs. No public bucket URL/UI is introduced.
- Domain errors: 400 invalid request/JPEG; 401 auth; 404 missing/foreign/no cover; 409 cover/object conflict; 413 too large; 502 upload/link/read/cleanup failure. Unexpected auth/config errors are generic 500; raw service/SQL details are not returned. Failure responses distinguish cleanup `removed`, `not_required`, `unconfirmed`. API Client preserves that state and never retries automatically.

## Security design / SQL Review

**Static Review: PASS, zero known BLOCKER.** This is not PostgreSQL execution or a live Storage PASS.

1. Private bucket with image/jpeg allowlist and 5 MiB limit. A pre-existing unexpected bucket ID makes migration fail rather than silently rewriting its settings.
2. Authenticated users get only a private object SELECT policy: exact canonical name, owned Wish and associated cover_path must all match. Restrictive read guard protects the bucket even if an unrelated permissive read policy exists. Restrictive INSERT/UPDATE/DELETE guards deny all ordinary writes to this bucket; anon guard denies all operations there. Other buckets retain their previous policy behavior.
3. Direct client writes are deliberately denied, rather than offering direct uploads which could bypass the Business API's signature validation. Storage upload/removal use a server-only service-role client after Bearer validation and a user-scoped Wish lookup. **Service-role bypasses RLS**: its safety comes from the gateway, fixed destination, non-upsert and server-only key, not from RLS protecting the privileged key. No service credential is imported/referenced by Desktop/shared packages or its built bundle.
4. Configure `SUPABASE_SERVICE_ROLE_KEY` only in the API server environment (`apps/api/.env.local` for local acceptance). .env.example documents the existing key name. Do not prefix it VITE_, place it in Desktop configuration, log it or expose it to callers. Missing server configuration fails closed before Storage writes. No real env file/key was modified in this round.
5. Service-only `attach_wish_cover(p_wish_id uuid,p_user_id uuid)` validates auth.role()=service_role, locks the exact Wish+owner, rejects an existing cover and derives its own canonical name. It checks the actual storage.objects metadata row under a share lock for JPEG MIME and nonzero size <=5 MiB, then updates only cover_path/updated_at. User ID is taken by API from the owned user-client lookup, never from submitted form fields. Clients cannot execute this RPC or directly UPDATE Wishes.
6. The metadata check does not inspect S3 bytes; byte validation is enforced at the sole ordinary upload gateway. Possession/compromise of the service key would bypass these boundaries as with any service-role access; no claim of RLS protection for that key is made.
7. Migration has 12 top-level statements inside BEGIN/COMMIT. No function-internal COMMIT/ROLLBACK, explicit table lock, new reward trigger or storage.objects metadata INSERT/DELETE. Existing 14 migrations, including deployed M3-01/M3-02, matched HEAD with normalized line endings.

## Cross-service failure / concurrency contract

There is **no distributed transaction** across Storage and Postgres, and no false atomicity/idempotency guarantee.

- Only the request whose non-upsert upload succeeded calls association. Other concurrent ordinary requests collide on the same object; they neither attach nor delete the winning object. Only the server may attach; ordinary callers cannot race a direct-link RPC around signature validation.
- After association error, user-scoped readback checks whether that canonical path committed. If it did, return success without deleting it. An unreferenced object is removed only after a definite SQL rejection, with the original successful upload proving this request created it. Removal always goes through Storage API `.remove([path])`, never DELETE storage.objects.
- Unknown upload outcome, unknown association commit with unreferenced readback, failed readback or failed deletion → explicit `COVER_CLEANUP_UNCONFIRMED`, cleanup=unconfirmed and structured `wish_cover_cleanup_unconfirmed` audit with Wish ID/path/stage. No automatic retry or potentially destructive delete is attempted. Confirmed compensated rejection reports COVER_LINK_FAILED / removed.
- API/UI retry after an uncertain outcome must first reconcile state. Orphans can block later uploads with an object conflict; inspect the recorded path/owner, reference state and bytes, then use an authorized Storage API cleanup if appropriate. No replacement/recovery UI is added here.
- Process termination between services can leave an orphan before any catch/audit executes. There is no durable upload journal/reconciliation worker in this minimal ticket. An operator follow-up may be needed; the implementation does not claim crash-proof cleanup or safety against concurrent privileged administrator mutation.
