## Implementation / static SQL review

- New `reschedule_task(date, task_id, target_date)` RPC is SECURITY DEFINER with empty search_path, explicit auth.uid ownership filtering and authenticated-only execution. No table write grant/RLS change or privileged frontend credential. Source/Planning ownership also follows existing composite FK constraints and the unique Planning Task index.
- Migration explicitly wraps function creation and ACL installation in BEGIN/COMMIT. It needs no LOCK TABLE, SET LOCAL, table alteration or backfill; old deployed migrations remain unchanged. This addresses the previously encountered CLI transaction-boundary issue without introducing a table-wide lock.
- Client action is strictly `{ date, taskId, targetDate }`. Zod validates real ISO calendar dates and relative source/target order; SQL decides user-timezone Today after acquiring locks. Invalid/missing/nonfinite dates, invalid timezone and unexpected resource/state changes fail closed. Next.js authenticates the Bearer token before creating a user-scoped RPC client; expected domain failures map to 400/401/404/409, unexpected details stay hidden.
- Lock order is settings SHARE → source Plan UPDATE → existing destination Plan UPDATE → Task UPDATE → source Item UPDATE → Planning UPDATE. Source < target ensures ascending Plan order, and no later Plan lock is requested after acquiring Task. This avoids a cycle with destination Commit/Draft commands waiting on the same Task.
- A fresh conflict query after the Task lock sees committed destination membership, including a destination Plan created during the earlier wait. Existing Draft/Add Later commands also lock the Task before inserting membership. If those commands execute after reschedule, their explicit later insertion is allowed; it is not a fabricated Item created by reschedule. Real concurrency execution remains pending.
- Pending→rescheduled updates only result_status/rescheduled_to_date/updated_at of the original Item. Its ID/Task/date relation, title/time, origin and priority stay frozen. The Task row is not copied or changed. The destination Plan and all existing Draft/Committed Items stay untouched.
- Existing Planning time pair/target_week/other metadata stay unchanged. A missing Planning row is created with the original source time snapshots (already validated by source constraints), then points to the requested target. An existing same-target Planning row needs no timestamp update. Target same-Task membership or an intervening Planning date rejects atomically.
- Same-source/same-target retry returns `changed=false` and the recorded source result without rewriting Planning or Item timestamps. This also acknowledges a previously successful request after its date has passed or the global Task has subsequently completed; it does not perform a new transition. A different target is rejected. The retry cannot undo a later schedule.
- Planning writes happen before the source Item write; any Item/qualification/reward trigger error rolls back the whole RPC. M2-02/M2-03 triggers are reused, not replaced. Since pending and rescheduled are both incomplete and remain in N, a legal reschedule does not change completion counters/qualification or grant/reverse an extra reward. An 80%-qualified day can remain qualified after one of its already-pending Items is rescheduled.
- GET Today adds `canReschedule` based on committed state, user date, source result and ordinary/open Task status. Desktop renders a compact action and native date dialog using existing styles; server Today determines the minimum date. Pending disables inputs/cancel/duplicate submit, errors retain the selected date for retry, success refetches, and the source displays `已改期 → 目标日期`. The prior Added Later response is typed with this new GET-only projection omitted; its SQL/API behavior is unchanged.
