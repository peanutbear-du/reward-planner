## Implementation and static migration review

- All TECH_SPEC §6.13 fields are present. A unique `(user_id, source_type, source_id)` constraint prevents duplicate Daily sources, including concurrent writes. A composite source/owner foreign key references `daily_plans(id, user_id)`; users cannot attach an event to someone else's plan, even through a privileged INSERT.
- This ticket accepts only `DAILY_QUALIFIED`, fixed `amount = 1`. Milestone source support requires a future migration with its own validated owner/source relation; no Milestone command, reward calculation, allocation, Wish, Pending Progress, API refactor, UI or dependency was added.
- Authenticated users have only SELECT plus owner-filtered RLS. PUBLIC/anon/authenticated have no event write grant. Both new SECURITY DEFINER functions pin empty search_path and revoke execution from PUBLIC/anon/authenticated/service_role. The per-plan helper also checks auth identity when present and filters the plan by both ID and owner. Trusted service-role table operations still bypass RLS; this is not treated as RLS protection.
- M2-01's RPCs already lock the owned Plan first. M2-02 updates persisted qualification inside those RPC transactions. A new AFTER trigger observes changes to `is_qualified`, then reconciles that same locked Plan. No qualification algorithm, count, timestamp or existing RPC contract is rewritten.
- false→true inserts active +1 or reactivates the existing event. true→false marks that event reversed at the actual reversal time. Reactivation clears reversed_at while retaining id, amount and original created_at. true→true / false→false do not call the ledger helper. A never-qualified plan gets no fabricated reversed event.
- Reward errors are not caught/swallowed in SQL: grant, reversal or reactivation failure aborts the entire command, including Task, Daily Item and persisted qualification. Added Later uses the same transaction boundary.
- The migration takes an ACCESS EXCLUSIVE Daily Plan table lock before installing schema/trigger/backfill, preventing a gap with concurrent qualification updates. Local lock timeout is 10 seconds and statement timeout 60 seconds. Apply the migration through the normal transactional migration runner; a lock/statement timeout must roll back and be retried, never bypassed manually. This lock can briefly block Daily commands/reads during deployment.
- Backfill loops over currently persisted qualified Committed plans and calls the same idempotent per-plan helper. It never reads/recomputes Items, rewrites snapshots or infers prior reward/reversal history. New created_at is actual observation time; historical qualified_at and all Plan/Task/Item fields are preserved. Repeating reconciliation leaves an existing active event byte-for-byte unchanged. The schema migration itself is applied once by migration version, not rerun as raw CREATE TABLE SQL.
